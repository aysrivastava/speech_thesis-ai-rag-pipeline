# ISL RAG Pipeline — Steps 1 to 7 (retrieval + context-aware LLM layer + enrollment)

This is a fresh, from-scratch implementation of the RAG groundwork you asked
for: MediaPipe extraction → chunking decision → embedding → local vector DB
→ semantic search test. None of it reuses the old codebase's code (though
it avoids a couple of bugs that codebase had — noted inline where relevant).
No LLM is wired in yet, on purpose — that's the deliberate next step once
you're satisfied retrieval itself works.

## Recording test clips with your webcam

Instead of recording on your phone and copying the file over, you can
record straight from your Mac's webcam and test it in one step:

```bash
python3 record_webcam_and_test.py
```

**Every round starts by asking how you want to test:**

```
How do you want to test?
   [1] Record from webcam (blind test)
   [2] Test an existing file from test_query_videos/
```

Pick `1` for a live demo, or `2` to re-run the test against a clip that's
already a file (useful for re-checking a specific take, or testing clips
that came from somewhere other than this tool). This is asked fresh every
round, so you can freely mix live demos with file re-tests in one session
— press Enter at that prompt to quit. Picking file mode never opens the
webcam at all, so there's no camera/overlay startup cost if you're just
testing files.

If you pick file mode, you get a numbered list of whatever's actually in
`test_query_videos/` to choose from.

**If you pick webcam mode, this is a blind test** — you are never asked
which sign you're about to perform. The first time you pick webcam mode,
it prints the list of signs currently in your vector DB purely for your
own reference (so you remember what you can test against), but that's
informational only; the system itself is never told which one you're
doing. The target recording duration defaults to a flat **5 seconds**
(comfortably covers a single sign) — press Enter to accept it, type a
custom number of seconds, or type `q` to go back to the mode prompt.

A 3-2-1 countdown gives you time to get into frame, then recording starts
automatically and auto-stops when the timer runs out (a progress bar and
a live "X.Xs left" countdown are on screen the whole time). SPACE stops a
recording early if you finish sooner than the timer, or skips the
get-ready countdown if you don't need it. The clip is saved into
`test_query_videos/` and step 5 runs against it immediately, printing the
system's blind guess — compare that yourself to whatever sign you actually
performed. You're then back at the mode prompt — press Enter there to
quit.

**Live landmark overlay:** the preview now draws what MediaPipe is
actually detecting, in real time — each hand's 21-point skeleton (magenta
= "Right", cyan = "Left"), the upper-body pose skeleton (green), and a
small cluster of face-area reference points (yellow: nose, eyes, ears,
mouth corners — see "Do we extract face landmarks?" below for exactly what
these are and aren't). It uses the exact same landmarker configuration as
the real extraction pipeline, so what you see is representative of what
gets extracted — a quick visual check that you're actually being detected,
instead of guessing. If it slows down your preview noticeably, set
`SHOW_LANDMARK_OVERLAY = False` near the top of `record_webcam_and_test.py`.

The guide box is always green — it's just a framing reference ("stay
inside this"), not a status indicator, and it doesn't require both hands:
plenty of signs are one-handed. Whether you're recording is shown only in
the top status text, never by the box changing color, so there's nothing
to misread as an error.

This isn't just convenience — a Mac webcam is natively landscape, which
sidesteps the exact framing mismatch (portrait phone selfie, hands barely
in frame) that caused the weak first result. Worth reading the comment at
the top of `record_webcam_and_test.py` about why the saved file is
deliberately *not* mirrored even though the on-screen preview is — it's a
real correctness issue (MediaPipe's left/right handedness detection), not
just a style choice.

## Do we extract face landmarks?

Short answer: not a dedicated face mesh, no — and the live overlay doesn't
add one either, it just visualizes points we already compute.

What's actually happening: MediaPipe ships several separate models —
HandLandmarker (21 points/hand), PoseLandmarker (33 points, upper+lower
body), and a *separate* FaceLandmarker (a dense ~468-point face mesh, the
kind you've probably seen in MediaPipe demo images). This pipeline only
ever ran the first two. The PoseLandmarker's 33 points happen to include
11 coarse face-area points as part of its own topology (indices 0-10:
nose, eyes, ears, mouth corners) — not a face mesh, just enough to roughly
locate the head and mouth. The webcam tool's overlay draws those 11 points
in yellow, which is what you're seeing when you see "face points" on
screen — it costs nothing extra and needed no change to the actual 225-dim
feature vector.

**Should we add a real face mesh to the embedding itself?** That's a
bigger, separate decision, not a drawing tweak:
- It's linguistically relevant for ISL — eyebrow raises, mouth shape, and
  head tilt are genuine non-manual grammatical markers, not just
  decoration, so there's a real accuracy argument for it.
- But it would mean: downloading and loading a third model
  (`face_landmarker.task`), adding ~468x3=1404 dims on top of the current
  225 (a 6-7x increase in per-frame feature size), updating
  `config.FRAME_FEATURE_DIM`/`EMBEDDING_DIM`, and **re-running steps
  01/03/04 on every clip you already have**, since the old and new feature
  vectors wouldn't be comparable.
- Given where you are (~2 months left, your professor's preference against
  over-complicating this), this pipeline deliberately holds off on it for
  now. Hands + pose already carry most of the signal for isolated-sign
  retrieval. If you want it later as a documented follow-up experiment,
  it only touches `landmark_extraction_utils.py` and `config.py` — nothing
  about the DuckDB schema or the embedding method has to change shape to
  support it, just the input dimension feeding into step 3.

## Architecture at a glance

```
data_raw_videos/*.mp4  (landscape, upper-body framing)
        |
        |  01: MediaPipe HandLandmarker + PoseLandmarker, VIDEO mode
        v
Per-frame landmark sequence (T, 225)
  = right hand(63) + left hand(63) + pose(99)
  "hold last known" on missed detections, not zero-fill
        |
        |  (02: chunking analysis - OPTIONAL, parked as future capability -
        |       clips are consistently ~5-7s, already one retrieval unit)
        |
        |  03: statistical motion-pooling embedding
        v
900-dim L2-normalized vector
  = [mean_pos | std_pos | mean_vel | std_vel]  (225 each), training-free
        |
        |  04: store
        v
DuckDB  (vector_db/sign_vectors.duckdb)
  table sign_embeddings(label, source_video, duration_sec, embedding)
        |
        |         record_webcam_and_test.py - asks each round:
        |           [1] webcam -> blind record (label never told to system)
        |                         + live hand+pose/face-point overlay (visual only)
        |                         -> saves test_query_videos/*.mp4
        |           [2] file   -> pick an existing test_query_videos/*.mp4
        |                            |
        v                            v
   05_semantic_search_test.py  <-----+
     query video -> same 01 extraction -> same 03 embedding
     -> cosine similarity vs every stored vector -> ranked list
        |
        v
   Best match label (the blind guess, for webcam mode)
        |
        v
```

**Exact tech stack, for your methodology section:**

| Stage | What it is | Package / method |
|---|---|---|
| Hand features | 21 landmarks x 2 hands x (x,y,z) | `mediapipe.tasks.python.vision.HandLandmarker`, VIDEO mode |
| Body features | 33 landmarks x (x,y,z) | `mediapipe.tasks.python.vision.PoseLandmarker`, VIDEO mode |
| Face features | none (dedicated mesh) — 11 coarse points come free from pose | n/a (see above) |
| Missing-frame handling | hold last known landmark | custom, in `landmark_extraction_utils.py` |
| Chunking | not needed — each clip is already one retrieval unit; parked as an optional future capability | `02_...py` (optional, not in the required run order) |
| Embedding/"model" | training-free statistical motion-pooling | mean/std of position + mean/std of velocity, `embedding_utils.py` |
| Embedding dimensionality | 900 | `config.EMBEDDING_DIM` |
| Similarity metric | cosine similarity | explicit NumPy (`retrieval_utils.cosine_similarity`) |
| Vector DB | local, file-based, no server | DuckDB (`duckdb` package) |
| LLM | none yet — deliberately deferred | step 6, not built |

## What embedding model is this using, and why?

Short version: a training-free "statistical motion-pooling" vector (mean
position, std position, mean velocity, std velocity, across all 225
MediaPipe landmark values per clip → 900 dims, L2-normalized for cosine
similarity). The full reasoning — including why this was chosen over
reusing the old BiLSTM checkpoint or training a new contrastive encoder
right away — is written out in the comment block at the top of
`03_converting_extractions_to_vector_embeddings.py`. Short reason: zero
training needed, fully interpretable, and lets you validate the entire
plumbing today. Upgrading to a trained embedding later only touches
`embedding_utils.py` — nothing else in the pipeline changes.

## Is chunking needed?

No — not for this dataset, and not required to run the pipeline. Your
clips are consistently ~5-7 seconds, one sign/sentence per file, so each
clip is already the right retrieval unit; `03_...py` embeds whatever is in
`features_extracted/` directly and never reads a chunking decision file.

`02_chunking_strategy_analysis.py` still exists but is now **optional** —
parked as a documented "future capability" rather than a required step.
It answers the question with your own data's clip-length statistics
rather than a guess, and writes `chunking_decision.json` with the numbers,
which is useful evidence for your thesis methodology section, but you
don't need to run it for the pipeline to work. Where it *would* matter:
if you later add long, continuous, multi-sentence ISL video (not pre-cut
clips) — that's when real chunking/segmentation becomes necessary, and
this script is where that logic would get built.

## Known macOS crash, already fixed in this version

If you hit a hard crash like:

```
F0000 ... Check failed: service_ Service is unavailable.
*** Check failure stack trace: ***
    @  ... DrishtiMetalHelper initWithCalculatorContext:
    @  ... TensorsToDetectionsCalculator::Open()
```

**Actual root cause (confirmed): this is a real regression in mediapipe
1.0.0/1.0.1 on macOS Apple Silicon**, affecting HandLandmarker,
PoseLandmarker, FaceDetector and FaceLandmarker — `TensorsToDetectionsCalculator::Open()`
unconditionally tries to construct a Metal GPU helper even on a CPU-only
graph, and aborts because no Metal service was registered. It is not
about which delegate you pass; it happens regardless. Confirmed by two
independent reports testing the exact same stack trace on M2/M5 Macs:
[mediapipe#6356](https://github.com/google-ai-edge/mediapipe/issues/6356)
(MediaPipe's own tracker — maintainers acknowledged it, no fix shipped yet
as of this writing) and [gladsjr/super-ta#411](https://github.com/gladsjr/super-ta/issues/411)
(independently confirmed mediapipe 0.10.35 runs the identical script
successfully where 1.0.1 crashes every time).

**The fix: `requirements.txt` now pins `mediapipe>=0.10.30,<1.0`** instead
of an unpinned `mediapipe`, which is what let pip silently resolve to the
broken 1.0.1 in the first place. Run this in your venv to apply it to an
existing install:

```bash
pip install "mediapipe>=0.10.30,<1.0" --force-reinstall
```

No code changes are needed for this - it's a package version issue, not a
script bug. (An earlier version of this README pointed at a different,
superficially similar GitHub issue — #5568 — and suggested forcing
`delegate=BaseOptions.Delegate.CPU` as the fix. That change is still in
`landmark_extraction_utils.py` and is harmless, but it was treating the
wrong cause: it doesn't touch the actual 1.0.x regression, which crashes
regardless of delegate. The version pin above is the real fix.)

It's specific to the macOS build (Metal is Apple-only), which is also why
it couldn't be caught in sandbox testing before you first ran this —
there is no GPU/Metal code path on Linux at all, and the sandbox had
pulled mediapipe 0.10.32 (pre-regression) by coincidence of timing, not
because the dependency was pinned.

## The two bugs this deliberately avoids (carried over from the old code)

1. **Zero-filling undetected hands/pose.** The old `03_extract.py` wrote an
   all-zero vector for any frame where detection failed. For a
   motion/velocity-based embedding, a hand "teleporting" to (0,0,0) for one
   frame is a huge fake spike. This pipeline holds the last known position
   instead.
2. **The HIDDEN=128 vs 256 config mismatch.** Not applicable here at all —
   this pipeline's embedding (step 3) needs no trained model and no hidden
   size, so that whole bug class can't happen. It only comes back if/when
   you integrate the BiLSTM as an alternative embedding later.

## If one label wins everything (embedding v2 + diagnostic)

Symptom: the same label (e.g. "hi how are you") is BEST MATCH at ~0.97 for most clips. Cause: v1 pooled raw image coordinates, so mean positions swamped the vector and every clip looked alike. v2 (default now) uses body-relative coordinates, hand shape and block-balanced statistics. Run `python3 08_diagnose_retrieval.py` to compare v1/v2 and mean-centering on your own clips (leave-one-clip-out accuracy, no MediaPipe needed). After changing versions re-embed: `python3 03_...py --force` then `python3 04_...py --rebuild`. Enrolled (step 7) signs must be re-enrolled. Validated on synthetic data only.

`08` compares five embeddings (v1; v2; v2 hand-invariant, which handles left-handed or mirrored front-camera clips; v3 time-ordered trajectory; v3 stats+trajectory), each with and without mean-centering, using leave-one-clip-out accuracy. Compare against chance (1/number of labels). Pick the winner in `config.py` (`EMBEDDING_VERSION`, `HAND_INVARIANT`, `RETRIEVAL_CENTERING`), then `03 --force` and `04 --rebuild`.

## Trained encoder (EMBEDDING_VERSION 4)

Training-free embeddings topped out near 25-30% on 20 signs (see `08`). `11_train_encoder.py` trains a small 1D-CNN that maps a clip to a 64-d embedding (augmentation: time warp, crops, scale, noise, simulated hand drop-outs) and reports held-out retrieval accuracy by clip-fold and by guessed signer id. `--final` saves `encoder/encoder.pt`; then set `EMBEDDING_VERSION = 4`, run `03 --force` and `04 --rebuild`. Needs `pip install torch`. Only plumbing was verified on synthetic data; real accuracy is unknown until you run it.

Setup (the key is read from the environment, never put it in code):


Run:

```

python3 07_enroll_new_sign.py --video test_query_videos/red.mp4 --label "Red"
python3 07_enroll_new_sign.py --list
python3 07_enroll_new_sign.py --delete "Red"
```

`record_webcam_and_test.py` also asks for the question each round once a key is set (Enter = none).

**How the decision works.** Retrieval gives cosine similarities; they become `r_i = softmax(sim_i / T)`. An LLM sees only the question and the top-k candidate labels (shuffled, no scores, no video) and returns a plausibility `p_i` in [0,1]. The final score is `r_i * (p_i + eps)^lambda`. So context can overturn retrieval only when the similarity gap is below `T * lambda * ln((1+eps)/eps)` (about 0.091 with the defaults); a clearly better visual match always wins. Knobs are in `config.py`.

Decisions printed: RETRIEVAL_ONLY, ACCEPT_TOP1, OVERRIDE (printed as a loud banner), NO_PLAUSIBLE_CANDIDATE, BELOW_SIM_FLOOR, CONTEXT_UNAVAILABLE (no key or bad reply, falls back to retrieval top-1), EMPTY_DB.

**Out-of-vocabulary fallback.** If nothing retrieved is plausible, a vision model looks at ~8 sampled frames (pass 1, blind), then proposes a label given the question and known vocabulary (pass 2, text only). You confirm before anything is stored (`vlm_confirmed`; typing your own label stores `manual`). A VLM reads pantomime, pointing and iconic gestures; it cannot reliably read arbitrary lexical signs, so treat its output as a hypothesis.

**`OOV_SIM_FLOOR` ships as `None`.** A max-similarity floor needs calibration on your data (see the hold-out experiment below). Use `--sim_floor` to try values.

**Database change.** `label` is no longer a primary key (several examples per sign are allowed) and rows carry `provenance`. An existing DuckDB file migrates automatically. Re-running step 04 deletes only `curated` rows and keeps enrolled ones.

**Enrollment caveats.** Enroll 2-3 recordings per new sign; retrieval scores each label by its best example. Same camera setup and signer as the rest of the DB. A mirrored clip swaps left/right hand blocks and will match poorly against unmirrored training clips; the burger demo clip is also PSL, not ISL, so use it for demo only, not evaluation.

## Left-hand / right-hand signers and testing your own clips (steps 13)
- `MIRROR_AUGMENT` (training) and `QUERY_BOTH_ORIENTATIONS` (retrieval) in `config.py` make the trained encoder (v4) robust to
  a signer using the other dominant hand. After pulling this change, **retrain**: `11_train_encoder.py --final --skip_cv`, then `03 --force`, `04 --rebuild`.
- Put YOUR recordings in `data_raw_videos2/<exact sign label>/take1.mp4 ...` (separate from `data_raw_videos/`, which is untouched),
  then run `python3 13_eval_own_clips.py`. It reports top-1/top-3 with and without the mirrored query and each sign's hand-detection rate.
  These clips are never added to the DB.
